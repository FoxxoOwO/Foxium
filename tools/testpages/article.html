How reader mode extracts a page

By ChroGecko Engineering, 20 November 2026

Reading mode keeps the words and throws away everything else. A browser that offers it has to decide, for every page, whether the document is an article at all, and then which part of the document holds the prose. Both questions are answered by heuristics that look at paragraph density, text length, link density and the nesting of elements around the text.

The extraction pass scores candidate containers. A container wrapped in a small number of elements, holding many long paragraphs and few links, wins. Sidebars, navigation lists, comment threads and newsletter boxes lose because their paragraphs are short and their link density is high. Advertising blocks usually contain a single image and almost no text, so they never reach the score needed to be chosen.

Once a container is chosen, the cleaner removes attributes, converts relative image sources, drops forms and scripts, and serialises the result as HTML. What the reader sees afterwards is a document built by the browser: one column, comfortable line height, images limited to the width of the column, and colours that follow the system theme.

Because the transformation happens in the page itself, turning reading mode off is a simple restore of the nodes that were replaced. Keeping the original nodes alive, rather than reloading the page, means the scroll position and any page state survive the round trip.

Availability is a separate, cheaper question: a page is probably readable when it has enough paragraphs of reasonable length outside of preformatted blocks. Running that check on every load costs almost nothing, which is what allows the browser to offer the feature only where it would actually work.
